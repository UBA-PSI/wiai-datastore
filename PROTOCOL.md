# WIAI Datastore – wire protocol v1

This document is the normative wire format of the WIAI Datastore. The Python server and the JavaScript client are
built against it independently. Where it differs from `PLAN.md` on byte-level or HTTP details, this document wins.
Key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

Base URL of the API: `https://wiai.uni-bamberg.de/datastore/api/v1`. The reverse proxy does not strip the
`/datastore/` prefix; the server routes the full path. All paths below are relative to the API base unless they start
with `/datastore/`.

## 1. Encodings and primitives

### 1.1 Byte encodings

| Name | Definition |
|---|---|
| `b64u(x)` | Base64url (RFC 4648 §5), **no padding**. Decoders MUST reject `=`, characters outside `A–Z a–z 0–9 - _`, and non-canonical encodings (unused trailing bits not zero). Simplest check: decode, re-encode, compare. Python's `base64.urlsafe_b64decode` is lenient; wrap it. |
| `hex(x)` | Lowercase hexadecimal. Used only in test vectors. |
| `u32(n)` | Unsigned 32-bit integer, big-endian, 4 bytes. |
| `lp(x)` | `u32(len(x)) ‖ x` (length prefix in bytes). |
| `ascii(s)` | The bytes of an ASCII string. All IDs in this protocol are ASCII. |
| `‖` | Concatenation. |

Where this document gives a decoded length, any other length is a validation error.

### 1.2 Crockford base32 with check bits (`b32c`)

Used for human-typed values: access IDs, invite codes, recovery codes.

- Alphabet (value 0–31): `0123456789ABCDEFGHJKMNPQRSTVWXYZ`.
- Encode `b32c(bytes)` (n bytes): take the 8n bits of `bytes`, most significant bit of each byte first; append
  `k = (5 − (8n mod 5)) mod 5` check bits, which are the first `k` bits of `SHA-256(bytes)`; split into 5-bit
  groups, most significant first; map each group through the alphabet. Output is uppercase.
- 12 bytes → 96 + 4 check bits → 20 symbols. 17 bytes → 136 + 4 check bits → 28 symbols.
- Decode (client input): uppercase; remove spaces, tabs, line breaks, `-` and `.`; map `O→0`, `I→1`, `L→1`;
  any other character outside the alphabet (including `U`) is an error; check the length; decode; recompute the
  check bits and reject on mismatch.
- On the wire (paths, JSON, tokens) only the canonical form is used: uppercase, no separators. The server is
  case-sensitive and validates the check bits.
- Display form: groups of 4 symbols joined by `-`.

Example: `b32c(00 01 02 … 0b)` = `000G40R40M30E209185Z` (display `000G-40R4-0M30-E209-185Z`).

### 1.3 Canonical JSON (`cjson`)

Used for everything that is signed, hashed or MACed, and for the KDF descriptor in AAD.

1. Allowed values: object, array, string, integer, `true`, `false`, `null`. No floats, no exponents.
2. Integers: 0 ≤ n ≤ 2^53 − 1, decimal, no sign, no leading zeros. (Python: `bool` is not an integer here.)
3. Strings (values and keys): only characters U+0020–U+007E except `"` and `\` (backslash). Therefore no escape sequences
   ever occur, and the UTF-8 encoding equals the ASCII encoding.
4. Objects: keys unique, sorted ascending by byte value. Arrays keep their order.
5. No whitespace anywhere. Output encoded as ASCII bytes.

Because of rule 3, `JSON.stringify` with recursively sorted keys (JavaScript) and
`json.dumps(obj, sort_keys=True, separators=(",", ":"))` (Python) produce identical bytes. Encoders MUST reject
values that break the rules. A receiver parsing a canonical object MUST reject duplicate keys and floats.

Example: `{"b":[1,true,null],"a":"x"}` → `{"a":"x","b":[1,true,null]}`.

### 1.4 Primitives

| Primitive | Parameters |
|---|---|
| Hash | SHA-256. |
| MAC | HMAC-SHA-256, 32-byte output. |
| KDF | HKDF-SHA-256 (RFC 5869), output 32 bytes. An **empty salt** is a zero-length byte string (WebCrypto: `new Uint8Array(0)`); RFC 5869 treats it as 32 zero bytes, and HMAC with an empty key equals HMAC with that key, so Python's `hmac.new(b"", ikm, sha256)` matches. |
| AEAD | AES-256-GCM, 12-byte nonce, 16-byte tag appended to the ciphertext (WebCrypto layout). |
| Password KDF | Argon2id version 0x13 (19), see 3.1. |
| ECDH | P-256. Shared secret = 32-byte x-coordinate (WebCrypto `deriveBits`, length 256). |
| Signature | ECDSA P-256 with SHA-256; signature is 64 bytes `r ‖ s` (IEEE P1363, each 32 bytes big-endian), exactly what WebCrypto produces. Low-S is not required. |
| Public keys | Uncompressed SEC1 point, 65 bytes, first byte `0x04` (WebCrypto `raw` export). Server checks length and first byte only; clients import with WebCrypto, which validates the point. |
| Private keys | 32-byte scalar `d`. Imported as JWK `{kty:"EC", crv:"P-256", d, x, y}` with `x`, `y` taken from the stored public key. |
| Random | `crypto.getRandomValues` (client), `secrets` (server). |

## 2. Identifiers and secrets

| Item | Generated by | Raw | Wire format | Regex / length |
|---|---|---|---|---|
| Scope ID | server | – | `<slug>-<suffix>`; slug from the app name, suffix 6 random symbols from `0123456789abcdefghjkmnpqrstvwxyz` (lowercase Crockford) | `^[a-z][a-z0-9]*(-[a-z0-9]+)*-[0-9a-hjkmnp-tv-z]{6}$`, total length ≤ 48 |
| Vault ID | client | `SHA-256(S_founder.pub)` | first 26 symbols of the plain Crockford encoding (5-bit groups of the hash, MSB first, no check bits) | `^[0-9A-HJKMNP-TV-Z]{26}$` |
| Access ID | client | 12 random bytes | `b32c`, 20 symbols | `^[0-9A-HJKMNP-TV-Z]{20}$` + check bits |
| Slot ID | client | 12 random bytes | `b64u`, 16 chars | `^[A-Za-z0-9_-]{16}$` |
| Record ID | client | `HMAC(K_id, utf8(name))` | `b64u`, 43 chars | `^[A-Za-z0-9_-]{43}$` + canonical |
| Slot token | client | HKDF output, 32 bytes | `b64u`, 43 chars | |
| Token hash | client/server | `SHA-256(token)` | `b64u`, 43 chars | |
| Invite secret | client | 17 random bytes | `b32c`, 28 symbols | |
| Recovery code | client | 17 random bytes | `b32c`, 28 symbols | |
| Roster hash | both | `SHA-256(cjson(body))` | `b64u`, 43 chars | |
| Escrow key ID | both | `SHA-256(E.pub ‖ S.pub)` | `b64u`, 43 chars | |

- **Vault ID** is self-certifying: anyone holding `S_founder.pub` can check it. The server checks it at creation.
- **Access IDs, slot IDs, vault IDs** are chosen by the client so that they can be bound into AAD and signatures
  before upload. A collision yields `409 access_id_taken` / `slot_id_taken` / `vault_exists`; the client picks new
  values. Slot IDs are never reused within a vault; access IDs are never reused globally, not even after the vault was purged (the server keeps a permanent table of retired access IDs).
- **Record names**: non-empty, well-formed Unicode (no lone surrogates), at most 1024 bytes in UTF-8, encoded as
  UTF-8 without normalisation. The library rejects other names.

### 2.1 Human-facing codes

| Code | Canonical form | Display |
|---|---|---|
| Access ID | 20 symbols | 5 groups of 4 |
| Invite code | access ID (20 symbols) ‖ invite secret (28 symbols) = 48 symbols | 12 groups of 4 |
| Recovery code | 28 symbols | 7 groups of 4 |

The client tells them apart by length after normalisation (20, 48, 28). Each part's check bits are verified
separately.

### 2.2 Bearer tokens

| Actor | Header |
|---|---|
| Slot (app user) | `Authorization: Bearer wds1.<access_id>.<b64u(token)>` |
| Operator tool | `Authorization: Bearer wdsop.<b64u(32 random bytes)>` |

The server stores `SHA-256(token)` per slot (raw 32-byte token, not its b64u text) and the SHA-256 of each operator
token (from Ansible configuration, of the full ASCII string `wdsop.…`). Comparisons use `hmac.compare_digest`.
The API never reads cookies.

## 3. Key hierarchy

### 3.1 Argon2id

KDF descriptor (`kdf`), canonical JSON, stored per slot by the server and returned to the client:

| Slot state | `kdf` |
|---|---|
| passphrase | `{"alg":"argon2id","m":65536,"p":1,"salt":"<b64u 16 bytes>","t":3,"v":19}` |
| invite (not redeemed) | `{"alg":"invite"}` |

- `m` in KiB, `t` iterations, `p` lanes, `v` Argon2 version. Output length 32 bytes; no secret, no associated
  data.
- Defaults: m = 65536 (64 MiB), t = 3, p = 1. Client acceptance window: 65536 ≤ m ≤ 262144, 3 ≤ t ≤ 10, p = 1,
  v = 19, salt exactly 16 bytes. Outside the window the client refuses to unlock (`IntegrityError`). The server
  checks the same window when storing a descriptor.
- Password input: the passphrase normalised to **Unicode NFC**, then UTF-8.
- `KEK = Argon2id(password, salt, m, t, p) ` (32 bytes).

### 3.2 Derived keys

All HKDF calls use SHA-256 and 32-byte output.

| Key | IKM | Salt | Info (ASCII) | Use |
|---|---|---|---|---|
| `K_wrap` | `KEK` (passphrase slot) or invite secret (17 bytes, invite slot) | empty | `wds1/slot-wrap` | AES-GCM key for the slot blob (type 0x02) |
| `token` | same as `K_wrap` | empty | `wds1/slot-auth` | bearer token; server stores `SHA-256(token)` |
| `K_enc[e]` | `VMK[e]` | empty | `wds1/record-enc` | AES-GCM key for records of epoch `e` |
| `K_id` | `NK` | empty | `wds1/record-id` | HMAC key for record IDs |
| `K_commit` | `NK` | empty | `wds1/history-commit` | HMAC key for history commitments |
| `K_state` | `NK` | empty | `wds1/local-state` | HMAC key for the local rollback state (7.4) |
| `C[e]` | `VMK[e]` | empty | `wds1/check/vmk` | roster commitment for epoch `e` |
| `C_nk` | `NK` | empty | `wds1/check/nk` | roster commitment for `NK` |
| `K_ecies` | ECDH shared secret | `eph.pub ‖ recipient.pub` (130 bytes) | `wds1/ecies` | AES-GCM key of one keyring entry |

- `VMK[e]`: 32 random bytes per epoch. Epochs are numbered from 1 and increase by exactly 1.
- `NK`: 32 random bytes per vault, never rotated.
- `record_id = b64u(HMAC(K_id, utf8(name)))`.

### 3.3 Slot key material

Every slot except escrow has two key pairs: `E` (ECDH) and `S` (ECDSA). The private keys are stored on the server
encrypted under `K_wrap` in a type 0x02 envelope. Plaintext (`cjson`):

```
{"keys":[{"e_d":"<b64u 32>","e_pub":"<b64u 65>","s_d":"<b64u 32>","s_pub":"<b64u 65>"}, …],
 "slot":"<slot_id>","v":1,"vault":"<vault_id>"}
```

- `keys` holds one or two key sets. Two only while a key renewal is pending (5.4): the set listed in the head roster
  and the new set. The client uses the set whose `e_pub`/`s_pub` equal the slot's entry in the verified head roster.
  Once the roster lists the new set, the client re-wraps with only that set (`PUT /slots/{access_id}`).
- After decrypting, the client checks `vault` (against the expected vault, if known) and finds its
  slot by `slot` in the roster.
- The escrow slot has no wrapped blob, no access ID and no token; its private keys exist only offline.

### 3.4 Escrow keys

- The operator holds a **current** and a **spare** escrow key pair set (each: `E` + `S`). The server is configured
  with both public sets; `GET /scopes/{scope}` returns them.
- Escrow key ID = `b64u(SHA-256(E.pub ‖ S.pub))`. The library pins the IDs of the current and the spare set (**active**
  sets) and may list earlier sets as **retired**, each with a retirement time `until` (Unix seconds). A roster chain may
  name an active or a retired set in each version; any other set is refused. Retired sets are valid for history only
  (6.5). Both lists are fixed by the library build (a build with pins ignores the `escrowPins` and `retiredEscrow`
  options, which exist for tests). The server knows only the two configured sets and never accepts a retired set in a
  new version.

## 4. Envelope `WDS1`

### 4.1 Layout

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `57 44 53 31` ("WDS1") |
| 4 | 1 | type |
| 5 | 1 | flags, MUST be `0x00` |
| 6 | 4 | epoch, `u32`; record epoch for type 0x01, `0` for all other types |
| 10 | … | type-specific, below |

The first 10 bytes are the **header**. Every AAD starts with the header, so magic, type, flags and epoch are
authenticated.

| Type | Meaning | Bytes after the header | Min. length | Max. length |
|---|---|---|---|---|
| `0x01` | record | nonce (12) ‖ ciphertext+tag | 38 | writes: `max_envelope_bytes` of the scope; reads and rekey: the ceiling bound `26738726` (7.1) |
| `0x02` | slot private keys | nonce (12) ‖ ciphertext+tag | 38 | 4096 |
| `0x03` | keyring entry (ECIES) | eph.pub (65, first byte `0x04`) ‖ nonce (12) ‖ ciphertext+tag | 103 | 16384 |
| `0x04` | reserved (rosters are signed plaintext JSON, section 6) | – | – | – |

Nonces are random. Envelopes travel as raw bytes in record bodies and as `b64u` strings inside JSON.

### 4.2 AAD per type

`H` = the 10 header bytes of the envelope being produced.

| Type | AAD |
|---|---|
| 0x01 record | `H ‖ lp(ascii(scope_id)) ‖ lp(ascii(vault_id)) ‖ lp(ascii(record_id)) ‖ lp(u32(version))` |
| 0x02 slot keys | `H ‖ lp(ascii(scope_id)) ‖ lp(ascii(vault_id)) ‖ lp(ascii(access_id)) ‖ lp(cjson(kdf))` |
| 0x03 keyring entry | `H ‖ lp(ascii(scope_id)) ‖ lp(ascii(vault_id)) ‖ lp(ascii(slot_id)) ‖ lp(u32(roster_version)) ‖ lp(recipient_E.pub)` |

- Record: `version` is the version the server stores (5.2). A reader computes the AAD with the version the server
  reports; a mismatch makes decryption fail → `IntegrityError`.
- Slot keys: `access_id` and `kdf` are the slot's own. An invite blob uses the invite's access ID and
  `{"alg":"invite"}`; at redemption the client re-wraps with the same access ID and the new argon2id descriptor. A
  server handing out a different salt or weaker parameters therefore yields a blob that does not decrypt.
- Keyring entry: `roster_version` is the version of the roster that the entry is uploaded with (6.4).

### 4.3 ECIES (type 0x03)

```
eph            = fresh P-256 key pair
Z              = ECDH(eph.priv, recipient_E.pub)                  32 bytes
K_ecies        = HKDF(IKM=Z, salt=eph.pub ‖ recipient_E.pub, info="wds1/ecies")
nonce          = 12 random bytes
ct             = AES-256-GCM(K_ecies, nonce, plaintext, AAD per 4.2)
envelope       = H ‖ eph.pub ‖ nonce ‖ ct          (H: type 0x03, flags 0, epoch 0)
```

Keyring entry plaintext (`cjson`):

```
{"epochs":[{"e":<epoch>,"k":"<b64u VMK[e], 32 bytes>"}, …],"nk":"<b64u NK>","v":1}
```

`epochs` is sorted by `e` ascending and lists exactly the epochs committed in the roster version it is uploaded
with. The client uses a key only if `C[e]` (or `C_nk`) derived from it equals the commitment in the verified head
roster; anyone can create an ECIES entry, so this check is what makes the entry trustworthy.

### 4.4 Record plaintext and padding

```
plaintext = u32(len(hdr)) ‖ hdr ‖ body ‖ zeros
hdr       = UTF-8 JSON object, at most 2048 bytes
```

| Header key | Type | Meaning |
|---|---|---|
| `n` | string | record name (section 2) |
| `k` | `"json"` or `"bytes"` | `json`: body is UTF-8 JSON text; `bytes`: body is the raw bytes |
| `l` | integer | body length in bytes |
| `t` | integer | client time of the write, Unix milliseconds |
| `m` | string, optional | MIME type for `bytes` (≤ 255 bytes) |

- Writers produce the header with `JSON.stringify` and sorted keys; readers parse it as ordinary JSON and ignore
  unknown keys. Readers MUST check `n` equals the requested name, `4 + len(hdr) + l ≤ len(plaintext)`, and that every
  padding byte is `0x00`.
- Total plaintext length is `padme(4 + len(hdr) + l)`.

**Padmé** (Nikitin et al., 2019), for an integer `L ≥ 1`, with `bitlen(x)` = number of bits of `x`
(`bitlen(0) = 0`; JavaScript: `32 − Math.clz32(x)`; Python: `x.bit_length()`):

```
E = bitlen(L) − 1            # floor(log2 L)
S = bitlen(E)                # floor(log2 E) + 1, and 0 for E = 0
z = E − S                    # low bits to clear, always ≥ 0
padme(L) = ceil(L / 2^z) · 2^z
```

| L | 1 | 3 | 9 | 40 | 100 | 1000 | 1025 | 4097 | 65537 | 1048577 | 10487812 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| padme(L) | 1 | 3 | 10 | 40 | 104 | 1024 | 1088 | 4352 | 67584 | 1081344 | 10747904 |

Record envelope length = `padme(…) + 38`. The server's size limit for a scope is
`max_envelope_bytes = padme(4 + 2048 + max_value_bytes) + 38`.

### 4.5 History commitment

With every record write (not rekey, not delete) the client sends

```
commit = b64u(HMAC(K_commit, lp(ascii(record_id)) ‖ lp(u32(version)) ‖ lp(SHA-256(plaintext))))
```

where `plaintext` is the full padded record plaintext (4.4). The server stores it with the version and never changes
it. Readers verify it after decrypting each version (`IntegrityError` on mismatch). Tombstones have no commitment.

## 5. Records, versions, epochs

### 5.1 Epochs

- A vault starts at epoch 1. The epoch increases by exactly 1 in a roster version that revokes or rotates (6.3).
- Record writes MUST use the vault's current epoch; otherwise `409 epoch_changed` (body includes `epoch`). The
  library then reloads slot and roster and retries once.
- Old-epoch blobs are re-encrypted in place by the owner (`PUT …/versions/{n}/rekey`). A roster version may stop
  committing an old epoch only when no stored blob uses it (`409 epoch_in_use` otherwise).

### 5.2 Versions and preconditions

- Versions per record ID start at 1 and increase by 1 per write or delete. They are never reused, also not after
  tombstones or history purges (the server keeps the counter for the record ID until the vault is purged).
- `ETag` of a record or version: strong, quoted decimal, e.g. `"7"`. `If-Match` carries exactly one such value;
  `W/`, lists and `*` are rejected with `400 bad_request`. `If-None-Match` accepts only `*`.

| Request | Precondition | Outcome |
|---|---|---|
| `PUT` record | `If-None-Match: *` | succeeds only if the record ID has never existed; stores version 1 |
| `PUT` record | `If-Match: "n"` | succeeds only if the latest version (live or tombstone) is `n`; stores `n+1` |
| `DELETE` record | `If-Match: "n"` | succeeds only if the latest version is `n` and live; stores tombstone `n+1` |
| `PUT` rekey | `If-Match: "e<k>"`, e.g. `"e3"` | succeeds only if the stored blob of that version has epoch `k` |
| any of the above | none | `428 precondition_required` |
| any of the above | not met | `412 precondition_failed` with `{"current": n or null, "deleted": bool}` (rekey: `{"epoch": k}`) |

A tombstoned record is recreated with `If-Match` on the tombstone version. The client puts the resulting version
(1 or `n+1`) into the AAD before uploading. Compare-and-swap runs inside one SQLite `BEGIN IMMEDIATE` transaction.

### 5.3 History retention

Per record the server keeps the latest `history_versions` versions (live and tombstones, including the latest).
Versions younger than 600 seconds are never dropped by count. Pruning runs after each write in the same transaction
and in a periodic sweep. All stored versions count against the quota.

## 6. Roster

### 6.1 Structure

A roster version is a signed document `{"body": <body>, "sig": "<b64u 64 bytes>"}`. The body (`cjson`):

| Key | Type | Meaning |
|---|---|---|
| `type` | `"roster"` | domain separation for the signature |
| `v` | `1` | format version |
| `scope` | string | scope ID |
| `vault` | string | vault ID |
| `version` | integer | 1, 2, 3, … |
| `prev` | string | `""` for version 1, else the roster hash of version `version − 1` |
| `epoch` | integer | current epoch from this version on |
| `commit` | object | `{"epochs":[{"c":"<b64u C[e]>","e":e}, …],"nk":"<b64u C_nk>"}`; `epochs` ascending, includes `epoch` |
| `slots` | array | slot entries, sorted by `id` (byte order) |
| `signer` | string | slot ID of the signing slot |
| `time` | integer | signer's clock, Unix seconds. The server does not check it; clients use it only to judge versions signed by the escrow slot of a retired set (6.5) |

Slot entry:

| Key | Type | Meaning |
|---|---|---|
| `id` | string | slot ID |
| `kind` | `"passphrase"`, `"invite"`, `"escrow"` | invite = not yet acknowledged by an owner after redemption |
| `role` | `"owner"`, `"write"`, `"read"` | |
| `e_pub` | string | b64u, 65 bytes |
| `s_pub` | string | b64u, 65 bytes |
| `expires` | integer or `null` | invite expiry, Unix seconds; `null` for other kinds |

Access IDs are deliberately **not** in the roster: members cannot see each other's access IDs. The binding
access ID → slot comes from the slot blob (AAD and plaintext, 3.3).

- **Roster hash** `h_n = SHA-256(cjson(body_n))`. The signature is not hashed, so ECDSA malleability cannot change
  a hash.
- **Signature**: `sig = ECDSA-P256-SHA256(S_signer, cjson(body))`.
- **Signer key**: version 1 – the `s_pub` of slot `signer` in version 1 itself, and the vault ID MUST equal the
  vault ID derived from that `s_pub`. Version n > 1 – the `s_pub` of slot `signer` in version n − 1, which MUST have
  role `owner` there (the founder, any other owner, or the escrow slot).

### 6.2 Invariants (checked by server and client)

1. Exactly one slot of kind `escrow`, role `owner`, `expires: null`, whose `(e_pub, s_pub)` is a configured escrow
   set (server: the current or the spare set, never a retired one) / an active or, in older versions of a chain, a
   retired escrow key ID (client, 3.4, 6.5). The escrow slot keeps its slot ID in every version (6.3).
2. At least one owner slot that is not escrow.
3. Version 1 contains exactly two slots: the founder (`passphrase`, `owner`, signer) and escrow. `epoch` = 1,
   `prev` = `""`.
4. `invite` slots have a non-null `expires`. Their role is `write` or `read`, or `owner` for an owner invite. An owner invite
   can only be *added* in a version signed by the escrow slot (recovery, 9); it may stay in later versions (founder versions
   included) until it is converted, and then follows the ordinary rules of 6.3 (its role and expiry cannot change). The
   rule is therefore checked per added slot (6.3), not per version.
5. At most 64 slots; `cjson(body)` at most 65536 bytes.
6. Slot IDs unique within the version.
7. `commit.epochs` contains `epoch`, all entries ≤ `epoch`, ascending, no duplicates.

### 6.3 Allowed changes from version n−1 to n

The server enforces these (it never verifies signatures; clients do, for the whole chain, and apply the same rules
where they can see the data: they cannot see `used`, so they accept the removal of any invite slot without an epoch
change).

| Change | Allowed when |
|---|---|
| `version` = head + 1, `prev` = head hash | always required; otherwise `409 roster_conflict` (compare-and-swap) |
| `epoch` | equal to the current epoch, or current + 1 |
| remove a slot | `epoch` = current + 1 (revocation), or the slot is an `invite` that was never authenticated (`used = false`); else `409 revocation_required`. Any non-escrow slot may be removed this way, owner slots included (see "Revoking owner slots" below). Never the escrow slot. Recovery completion (9) removes nothing |
| add a slot | new slot ID never used in this vault; kind `invite` with server material in `new_slots`; the added slot is checked on its own: an owner invite only if the signer is the escrow slot (an owner invite that is already in the roster may stay unchanged in later versions) |
| escrow slot ID | never changes: the escrow slot is neither removed nor replaced by a slot with another ID (`400 invalid_roster`; the client verifier refuses such a chain) |
| `e_pub`/`s_pub` of a slot | (a) the slot is the signer and has role `owner` (an owner changes only its own keys; another owner's keys, also those of a redeemed owner invite, are never signed in by someone else: `400 invalid_roster`; if the new keys equal the slot's pending renewal, that renewal is cleared); or (b) a non-owner slot: they equal the slot's pending renewal (7.2), which is cleared (`409 renewal_mismatch` otherwise); or (c) the escrow slot switching to the other configured escrow set (the escrow slot keeps its slot ID; this is how an owner replaces a retired set, 6.5) |
| `kind` invite → passphrase | only if the server has recorded the slot's redemption |
| `expires` | `null` together with invite → passphrase; otherwise it never changes (an invite cannot be extended) |
| `role` | write ↔ read for non-owner slots; owner roles never change |
| `commit.epochs` | may drop an epoch only if no stored blob uses it (`409 epoch_in_use`). An existing commitment (and the NK commitment) never changes; the only epoch that may be added is the new current one (`400 invalid_roster`) |
| no-op | a version identical to the head apart from `version`, `prev`, `time` and `signer` → `400 invalid_roster` |
| `scope`, `vault`, `type`, `v` | never |

A revocation is a roster version with `epoch` = current + 1 that removes one or more slots. There is no separate
revocation endpoint. The client MAY also raise the epoch without removing a slot.

**Revoking owner slots.** The server allows the removal of an owner slot with an epoch bump like that of any other slot;
which owner slots a client offers to revoke is a signer-side policy (PLAN 5.7), not part of the chain verification: an
owner may revoke an owner slot that the escrow slot added (recovery); an owner whose own slot was added by the escrow
slot may revoke any other owner slot; owners that were not added by the escrow slot never evict each other; nobody
revokes the escrow slot or its own slot. "Added by the escrow slot" is read from the signed chain (the version that
added the slot is signed by the escrow slot).

**Recovery versions (escrow-signed).** An escrow-signed version is accepted only through the operator's recovery
completion (9), never through `POST /vaults/{v}/roster`. It is limited to what the client verifier accepts: the same
`epoch`, an identical `commit` object, every existing slot (the escrow slot included) unchanged in every field, nothing
removed, and exactly one added slot of kind `invite` and role `owner`. The server answers `400 invalid_roster` to
anything else, so it can never store a head that every client would reject. The other rules above (slot ID and access ID
never used, invite expiry window, `version`/`prev`, no-op) apply as usual.

**Expired invites.** An unredeemed invite whose `expires` has passed is dead on the server (its token answers
`410 invite_expired`), but its slot stays in the roster: removing it needs a roster version, every roster version needs
an owner's signature, and the server holds no signing key (and a version it made up would fail every client's chain
check). The server therefore never removes expired invite slots by itself. Instead the library's owner maintenance on
unlock removes them (`maintain`, unless the app unlocked with `maintain: false`): all unredeemed, expired `write` and
`read` invites go in one version. If none of them was ever used, that version keeps the epoch; if one was used
(`used = true`: a request with its token was accepted, which already returns its keyring entry), the same version is a
revocation (`epoch` + 1), and the re-encryption continues through the resumable rekey. Expired owner invites (recovery)
are left alone. The same rule applies when an owner withdraws an invite by hand: an invite that was never used is removed
without a new epoch, any other invite only by a revocation (`409 revocation_required` otherwise).

**Roster growth is bounded** (a vault owner could otherwise fill the disk with roster versions, which are not records).
Per vault the server stores at most 1000 ordinary versions; a *protective* version (it removes a slot, drops an epoch,
adopts a renewal or switches escrow) may go on up to 1100 versions in total. Beyond that: `507 quota_exceeded` with
`limit` = `roster_versions`. The bytes of all stored versions (body, signature, new slot blobs) are tracked per vault: an
ordinary version is refused with `507 quota_exceeded` / `limit` = `roster_bytes` above 16 MB (2^20 bytes each) and counts toward
`vault_bytes` and `scope_bytes`; protective versions are never refused for quota reasons.

### 6.4 Keyring rule

Every roster upload (creation, `POST …/roster`, recovery) carries **one keyring entry for every slot** of the new
version, including escrow, each encrypted to that slot's `e_pub` in the new version, with `roster_version` = the new
version in the AAD, containing the keys of exactly the committed epochs plus `NK`. The server replaces the whole
keyring atomically. Before encrypting to a slot the owner's client takes `e_pub` only from the verified roster.

### 6.5 Client verification

The client fetches all versions, verifies version 1 against the vault ID, then each signature, `prev` link,
invariants and allowed changes, and pins the head hash and version in its local state (7.4). A head older than the
pinned one, or a different hash at the pinned version, is an `IntegrityError`. A version signed by escrow marks the
vault "recovered by the faculty" for the UI.

**Escrow sets in the chain** (3.4). Every version names the escrow set in its escrow slot, and that set must be active
(pinned) or retired in the library; any other set is an `IntegrityError`. Retired sets are valid for history only:

- A version signed by the escrow slot counts only if the signer's set is active, or retired with `time ≤ until` of that
  set; otherwise the chain is refused. An escrow-signed version never changes an existing slot (6.3), so a recovery
  cannot swap the escrow keys.
- A head that still names a retired set is read like any other (status `escrowRetired`). An owner's client replaces it on
  unlock by an owner-signed version that switches the escrow slot to an active set (6.3 (c)); until then it refuses every
  other roster edit, so that no keyring entry is encrypted to a retired key (6.4). If a recovery notice is still
  unacknowledged, the replacement waits for it.
- Residual risk: `time` is chosen by the signer. A leaked retired escrow key plus a colluding server can backdate a
  version on a vault that was not opened since the retirement and whose head still names the retired set, on a device
  without a pinned newer head. A pinned head (7.4) protects every device that has opened the vault before.

## 7. Limits and other objects

### 7.1 Scope limits

| Limit (JSON key) | Default | Ceiling | Meaning |
|---|---|---|---|
| `max_value_bytes` | 10485760 | 26214400 | max. record body (plaintext value) of a new write |
| `max_envelope_bytes` | derived | derived | `padme(4 + 2048 + max_value_bytes) + 38`; default `10747942`, ceiling `26738726` |
| `vault_bytes` | 209715200 | 1073741824 | sum of envelope lengths of all stored versions in a vault, plus its roster bytes (below) |
| `scope_bytes` | 2147483648 | 10737418240 | same, summed over the scope |
| `max_vaults` | 50 | 500 | vaults per scope |
| `history_versions` | 10 | 50 | versions kept per record (5.3) |

**What counts toward `vault_bytes` and `scope_bytes`.** Record envelopes (every stored version) and roster bytes (body,
signature and new slot blobs of every roster version; capped separately, 6.3 "Roster growth"). A record `PUT` compares
the vault's record bytes plus roster bytes with `vault_bytes`, and the sum of both over all vaults of the scope with
`scope_bytes`; an ordinary `POST …/roster` does the same with its own bytes added. Deletes, history purges, rekey and
protective roster versions are never refused for quota reasons, so a vault whose roster history reached the quota can
still free space. `GET …/usage` reports `bytes` as the sum of record envelopes only. Keyring entries replace each other
and are bounded by 4.1 and 6.2.

**Lowering limits never locks data.** `max_value_bytes` bounds new writes only (`413 value_too_large`). Reading and
re-encryption never use the scope's current limit: clients accept record envelopes up to the ceiling bound
`padme(4 + 2048 + 26214400) + 38 = 26738726` bytes, and a rekey `PUT` (8.5) is bounded by the ceiling of the server
configuration (the same value by default) and by the stored blob's length. `PATCH /admin/scopes/{scope}` refuses a
`max_value_bytes` whose `max_envelope_bytes` is smaller than the largest envelope stored in the scope (all versions,
also in vaults that are deleted but not yet purged): `409 limit_below_stored_value` (9). Lowering `history_versions`
prunes older versions (5.3).

### 7.2 Renewal statement

`{"body": <body>, "sig": "<b64u 64 bytes>"}`, body (`cjson`):

```
{"e_pub":"<new b64u>","rv":<head roster version seen>,"s_pub":"<new b64u>","scope":"…","slot":"<slot_id>",
 "type":"renewal","v":1,"vault":"…"}
```

Signed with the slot's `S` key as listed in the head roster. The owner's client verifies it against the head
roster's `s_pub` for that slot (a statement signed with an older key is discarded), then signs a roster version
with the new keys (6.3 b). A renewal is sent only with the redemption of an invite (8.4). The server keeps at most one pending renewal per slot and clears
it when a roster version adopts it.

### 7.3 Recovery code hash

`recovery_hash = b64u(SHA-256(code_bytes))` with `code_bytes` the 17 raw bytes. Sent at vault creation; the server
compares in constant time.

### 7.4 Local rollback state (client only)

localStorage key `wds:<scope>:<access_id>:state`, value `cjson({"mac":…,"state":…})` with

```
state = {"access":"<access_id>","epoch":e,"head":"<roster hash>","records":[["<record_id>",version], …],
         "rv":n,"scope":"<scope>","slot":"<slot_id>","vault":"<vault_id>"}
```

(`records` sorted by ID; `cjson` sorts the keys) and `mac = b64u(HMAC(K_state, cjson(state)))`. `access`, `scope`, `slot` and
`vault` bind the state to the slot that wrote it: a state in which any of the four differs from the unlocked slot (a
state copied from another member or another vault) is treated like an invalid one, and a state without them is
invalid. Missing, invalid or non-matching state counts as a new device (visible notice) and gives no rollback
protection for that session.

## 8. HTTP API

### 8.1 Conventions

- JSON bodies: `Content-Type: application/json` (charset parameter allowed, UTF-8 only), at most 1048576 bytes.
  Record bodies: `application/octet-stream`. Wrong type → `415 unsupported_media_type`.
- Requests with a body MUST carry `Content-Length` (`411 length_required`); the server checks it against the limit
  **before** reading (`413`), and the token **before** both.
- Unknown JSON keys in requests are rejected (`400 bad_request`).
- Times are Unix seconds (integers). Sizes are bytes.
- Every API response: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `Strict-Transport-Security: max-age=31536000`, plus the CORS headers (8.8).
- Errors: `{"error": "<code>", "message": "<English text>"}` plus code-specific keys (8.9).
- Check order on every request: route → CORS → authentication (401/429) → vault/scope state (410/403) → role (403)
  → read-only mode (503) → headers (428/400/415/411/413) → body → structure (400) → state checks in a transaction
  (409/412/507).

### 8.2 Authentication and roles

- Slot token: look up the access ID, compare `SHA-256(token)` with the stored hash. On `/vaults/{v}/…` the token's slot
  MUST belong to vault `v`; on `/slots/{access_id}/…` the token's access ID MUST equal the path's. Otherwise
  `403 forbidden`.
- Role comes from the slot's entry in the **head roster**. A redeemed invite still listed as `invite` acts with its
  roster role. An invite that is **not yet redeemed** is accepted only on `GET /slots/{access_id}`,
  `POST /slots/{access_id}/redeem`, `GET /vaults/{v}/roster`, and on `PUT /slots/{access_id}`
  (which answers `409 not_redeemed`); on every other endpoint it answers `403
  forbidden`. Whoever holds the invite code can therefore not read or write records before the redemption; the code does open
  the slot's own blob and keyring entry (the vault keys), which is why an invite that was used is withdrawn like a member,
  by a revocation (6.3). Every request that presents a valid, unexpired token marks the slot as *used*, also one that is
  then answered with `403`; the owner sees it as `slots[…].used` in the roster response (8.5).
- Revoked access IDs answer `401 revoked`; expired unredeemed invite tokens answer `410 invite_expired`; unknown or
  wrong tokens `401 unauthorized` with `WWW-Authenticate: Bearer realm="wds"`.
- Role column below: **any** = owner, write, read; **write** = owner, write; **owner** = owner.

### 8.3 Endpoints without token

#### `GET /scopes/{scope}`

`200`:

```
{"scope":"notenrechner-k7m2a9","name":"Notenrechner","status":"active"|"suspended",
 "enrollment":"join_code"|"open","read_only":false,
 "limits":{"history_versions":10,"max_envelope_bytes":…,"max_value_bytes":…,"vault_bytes":…},
 "kdf":{"alg":"argon2id","m":65536,"p":1,"t":3,"v":19},
 "escrow":[{"id":"…","e_pub":"…","s_pub":"…","status":"current"},{"id":"…","e_pub":"…","s_pub":"…","status":"spare"}],
 "library":{"latest":"1.0.0","deprecated":["…"]},
 "privacy_url":"https://wiai.uni-bamberg.de/datastore/…",
 "sandbox":null | {"enabled":true,"wipe_at":"03:30","timezone":"Europe/Berlin","next_wipe":1795000000,"last_wipe":1794913800 | null}}
```

`404 not_found` for unknown or deleted scopes. `kdf` lacks `salt`: the client draws one. `library.deprecated`
lists versions that should show the advisory banner.

`sandbox` is `null` for every scope except the public sandbox (PLAN 17). For it: `enabled` (false: creation and invite
redeeming answer `503 sandbox_disabled`), `wipe_at` and `timezone` (local time of the nightly wipe), `next_wipe` (Unix seconds of
the next scheduled wipe instant) and `last_wipe` (the instant of the last completed wipe, or `null`). Every vault of the sandbox
that was created before a wipe instant is deleted by the first maintenance sweep after it, so a client that remembers when it
first stored an access ID can tell that the vault is gone when that time is earlier than `last_wipe`. In the sandbox the
scope has open enrollment (`enrollment` is `"open"` only there, `"join_code"` for every other scope; it is derived, not stored) and the vault has no recovery: every recovery and escrow endpoint of the operator API answers `409 sandbox_no_recovery`.
At most `invite_slots` (default 3) invites exist per vault (`409 invite_limit`, `limit`), and an invite must expire at or before
`next_wipe` (`400 invalid_roster`). A vault deleted by its owner is purged at once.

#### `GET /slots/{access_id}/kdf`

`200 {"kind":"passphrase"|"invite","kdf":{…}}`. `404 not_found` for unknown or revoked IDs (counts as an
authentication failure for rate limiting, 8.7). `410 vault_deleted` for the slots of a deleted vault (not counted).
`400 bad_request` for malformed IDs or wrong check bits. A lookup of an existing, non-revoked ID is never throttled and
never counted (the descriptor is public, and one person behind a shared NAT must not be able to stop everyone else
behind it from unlocking).

#### `GET /pwned/{prefix}` – breach check of the passphrase dialogs

No token, no scope. `prefix` is exactly five uppercase hex characters, the start of the SHA-1 of the passphrase. The server
fetches `https://api.pwnedpasswords.com/range/<prefix>` with `Add-Padding` on the client's behalf (configuration `[server] pwned_url`;
empty switches the proxy off), caches the answer in memory (bounded, 24 h), and never logs the prefix. `200` with
`text/plain`: lines `SUFFIX:COUNT` (35 uppercase hex characters, CRLF), lines with count 0 are padding; `Access-Control-Allow-Origin: *`,
`Cache-Control: no-store`. `400 bad_request` for a malformed prefix; `429 rate_limited` (`Retry-After`; 120 per minute per client, IPv6 per /64);
`503 pwned_unavailable` (`Retry-After: 60`) when the service is unreachable, answers malformed or the proxy is off; after one failure the server
answers 503 at once for 60 s. The client treats everything but `200` as "unavailable" and falls back to its local estimator. The passphrase
and the full hash never leave the browser.

#### `POST /scopes/{scope}/vaults` – create vault

Request:

```
{"vault":"<vault_id>",
 "roster":{"body":{…version 1…},"sig":"…"},
 "slots":[{"slot":"<founder slot_id>","access_id":"…","kdf":{…argon2id…},"token_hash":"…","wrapped":"<b64u type 0x02>"}],
 "keyring":{"<founder slot_id>":"<b64u type 0x03>","<escrow slot_id>":"<b64u type 0x03>"},
 "recovery_hash":"<b64u 32>",
 "join_code":"…" | null}
```

Server checks: scope exists and `active`; join code (every scope except the sandbox: code
compared after normalising – trim, uppercase, remove spaces and `-` – in constant time, wrong → `403
join_code_invalid`, counts as authentication failure); `max_vaults` (`403 vault_limit_reached`; in the sandbox the server first purges
the oldest vaults that were created and last written at least `evict_min_age` ago, and answers `403 vault_limit_reached` only when none
qualifies); creation rate (8.7; the sandbox has two more counters, below); roster version 1 per 6.1/6.2; vault ID = derivation from the founder's `s_pub`; `slots` holds exactly the
founder slot; `keyring` exactly the roster's slots; envelope structures; uniqueness (`409 vault_exists`, `access_id_taken`). Read-only mode → `503 read_only`. The join code lives in the body,
so it is compared after the body has been parsed and structurally validated (a malformed body answers `400` before
the code is looked at).

`201 {"vault":"…","epoch":1,"roster_version":1,"head":"<roster hash>"}`.

A vault without any record 7 days after creation is purged.

### 8.4 Slot endpoints (token)

#### `GET /slots/{access_id}` – any

```
{"access_id":"…","slot":"<slot_id>","vault":"…","scope":"…",
 "kind":"passphrase"|"invite","role":"owner"|"write"|"read","sv":3,
 "kdf":{…},"wrapped":"<b64u>","expires":null|t,
 "keyring":{"rv":n,"entry":"<b64u>"} | null,
 "epoch":e,"roster":{"version":n,"head":"<hash>"},
 "renewal_pending":false,
 "recovery":null|{"requested":t,"ready_at":t}}
```

`kind` is the server's view: `passphrase` once redeemed. `sv` is the slot version (increments on every change of
`kdf`, `token_hash` or `wrapped`). `recovery` is shown to owner slots only (founder notice, 9.2). `keyring` is `null` only
if the server has no entry for the slot, which a consistent server never answers (6.4 gives every slot an entry); the
client treats it as an `IntegrityError`.
A request with an unredeemed invite token marks the slot as used on the server (6.3, 8.2), and this very response already
contains the keyring entry.

#### `PUT /slots/{access_id}` – any, passphrase slots only

Change passphrase or re-wrap. Header `If-Match: "<sv>"` (`428`/`412` as in 5.2, 412 body `{"current": sv}`).
Body `{"kdf":{…argon2id…},"token_hash":"…","wrapped":"…"}`. `200 {"sv": sv+1}`. The old token stops working
immediately if `token_hash` changed. Invite slots → `409 not_redeemed`.

#### `POST /slots/{access_id}/redeem` – invite token

Body `{"kdf":{…argon2id…},"token_hash":"…","wrapped":"…","renewal":{"body":…,"sig":…}}`. `wrapped` contains the
invite key set and the new key set; `renewal` announces the new set (7.2). Server: slot is an unredeemed invite
(`409 already_redeemed`), not expired (`410 invite_expired`), renewal body matches slot/vault/scope and its `rv`
is at most the head version. Atomically
stores the new KDF, token hash, blob, pending renewal, and the redemption time. `200 {"sv": …}`.

### 8.5 Vault endpoints (token)

| Method and path | Role | Request | Success |
|---|---|---|---|
| `GET /vaults/{v}/roster[?since=n]` | any | – | `200` see below |
| `POST /vaults/{v}/roster` | owner | see below | `200 {"version":n,"head":"…","epoch":e}` |
| `GET /vaults/{v}/records[?after=<rid>&limit=k]` | any | – | `200` list |

**Roster GET** `200`:

```
{"head":n,"head_hash":"…","epoch":e,
 "versions":[{"body":…,"sig":…}, …],               // versions > since (default since=0: all), ascending
 "slots":{"<slot_id>":{"used":bool,"redeemed":t|null,"expired":bool,"renewal":{"body":…,"sig":…}|null}, …}}
```

`slots` is server state for every slot of the head roster except escrow (`used`: the token was ever accepted).

**Roster POST** request:

```
{"roster":{"body":{…},"sig":"…"},
 "keyring":{"<slot_id>":"<b64u type 0x03>", …},       // exactly the slots of the new version (6.4)
 "new_slots":[{"slot":"…","access_id":"…","kdf":{"alg":"invite"},"token_hash":"…","wrapped":"…"}]}
```

`new_slots` lists server material for exactly the slots added in this version; it may be omitted when no slot is added
(equivalent to `[]`; the library omits it). Server checks 6.2 and 6.3 and
invite expiry (`now < expires ≤ now + 15 days`). On success, atomically: store the version, replace the keyring,
create new slots, delete removed slots (their access IDs become `revoked`), set the epoch, clear adopted renewals.
Errors: `400 invalid_roster`, `400 invalid_keyring`, `400 bad_request` (malformed `new_slots`), `409 roster_conflict` (body
`{"head":n,"head_hash":"…"}`), `409 revocation_required`, `409 renewal_mismatch`, `409 epoch_in_use`, `409 slot_id_taken`,
`409 access_id_taken`, `507 quota_exceeded` (6.3), `503 read_only` (8.6).

**Record list** `200` (sorted by ID, `limit` default and maximum 1000, `after` exclusive):

```
{"records":[{"id":"<rid>","version":n,"epoch":e|null,"size":bytes|0,"updated":t,"deleted":bool}, …],"next":"<rid>"|null}
```

Tombstoned records are included (`deleted: true`, `epoch: null`, `size: 0`) so that clients learn the version.

**Record GET** `200`, body = envelope, headers `Content-Type: application/octet-stream`, `ETag: "n"`,
`WDS-Commit: <b64u>`. A tombstone answers `404 deleted` with `{"version":n}`; a never-written ID `404 not_found`.
The same headers apply to `GET …/versions/{n}` (`404 not_found` for pruned versions, `404 deleted` for
tombstones).

**Record PUT** headers: `Content-Type: application/octet-stream`, `Content-Length`, `If-Match` or
`If-None-Match`, `WDS-Commit: <b64u 32 bytes>` (missing or malformed → `400 bad_request`). Server checks:
type 0x01, flags 0, length 38…`max_envelope_bytes` (`413 value_too_large`), epoch = current
(`409 epoch_changed`), precondition (5.2), quota after pruning, with the vault's roster bytes counted (7.1) (`507 quota_exceeded`, body
`{"limit":"vault_bytes"|"scope_bytes"}`). Response `{"version":n,"epoch":e,"size":bytes}` with `ETag: "n"`.
Malformed envelopes → `400 malformed_envelope`.

**History list** `200`, newest first:

```
{"id":"<rid>","current":n,"versions":[{"version":n,"epoch":e|null,"size":bytes,"created":t,"deleted":bool,"commit":"…"|null}, …]}
```

**Rekey list** `200`, items sorted by (record ID, version), only blobs with epoch < current:

```
{"epoch":e,"remaining":count,"items":[{"id":"<rid>","version":n,"epoch":k,"size":bytes}, …],"next":"<cursor>"|null}
```

`cursor` is opaque; `limit` default and maximum 500.

**Rekey PUT**: envelope type 0x01 with epoch = current and exactly the stored blob's length, precondition
`If-Match: "e<k>"` with k < current. The commitment is kept. Allowed in read-only mode and in a suspended scope. The size
bound is the ceiling bound of 7.1, not the scope's current limit (a blob stored under a higher limit must stay
re-encryptable). Answers, in the order the server checks them: `428`/`400` for a missing or malformed `If-Match`,
`415`, `411`, `413 value_too_large` above the ceiling bound, `400 malformed_envelope`; then in the transaction
`409 epoch_changed` (body `{"epoch":current}`) when the envelope's epoch is not the current one, `400 bad_request` when
k ≥ current, `404 not_found` for an unknown or pruned version, `404 deleted` (`{"version":n}`) for a tombstone,
`412 precondition_failed` (body `{"epoch":stored}`) when the stored blob is not under epoch k, and `400
rekey_size_mismatch` when the length differs. The library treats `412` (somebody else was faster) as done and
`409 epoch_changed` as "reload the roster and start over".

**Usage** `200`:

```
{"bytes":n,"records":n,"versions":n,"old_epoch_blobs":n,"read_only":bool,
 "limits":{"history_versions":…,"max_envelope_bytes":…,"max_value_bytes":…,"vault_bytes":…}}
```

Deleted vaults answer `410 vault_deleted` on every vault and slot endpoint.

### 8.7 Rate limits

In memory, sliding 60-second (or 3600-second) windows, client IP from `X-Forwarded-For` only when the peer is the
reverse proxy (uvicorn `--forwarded-allow-ips`).

| Counter | Counts | Limit |
|---|---|---|
| failures per IP | wrong/unknown/revoked token (a missing `Authorization` header answers 401 and is not counted), unknown or revoked access ID on `…/kdf`, wrong join code, wrong recovery code, wrong operator token | 60 per 60 s |
| failures per (IP, access ID) | failures naming that access ID | 10 per 60 s |
| vault creation per IP | every `POST /scopes/{scope}/vaults` that passes JSON parsing | 30 per 3600 s |
| sandbox creation per IP | the same requests for the sandbox scope, counted per IPv4 address or IPv6 /56 (`create_ipv6_prefix`) | 20 per 3600 s (`create_per_ip`, `create_window`), `429 rate_limited` |
| sandbox creation, all clients | the same requests, one counter for the whole sandbox | 60 per 600 s (`create_global`, `create_global_window`), `503 sandbox_busy` with `Retry-After` |

A sandbox vault that its owner deletes within `create_window` of its creation gives its creation back to both sandbox counters.

- A request with a valid token is never throttled: the token is checked first. Lookups of existing, non-revoked access
  IDs on `…/kdf` and the public GETs (`/scopes/{scope}`, `healthz`) are never throttled.
- IPv6 clients are counted per /64 (IPv4-mapped addresses as IPv4); the sandbox counters use the shorter prefix of the table.
- `429` applies only where failures are counted: token endpoints, `…/kdf` for unknown IDs, vault creation in `join_code`
  mode, recovery start with a code, operator endpoints. While an IP is over its budget, even a correct join code or
  recovery code from that IP is refused with `429` (the comparison is skipped); valid slot tokens still work.
- Over a limit, unauthenticated requests and requests with invalid tokens from that IP (and, for the second counter,
  for that access ID) get `429 rate_limited` with `Retry-After: <seconds>`.
- `409`, `412` and other non-authentication errors never count.

### 8.8 CORS

On every response under `/datastore/api/` (including errors and `429`):

```
Access-Control-Allow-Origin: *
Access-Control-Expose-Headers: ETag, Retry-After, WDS-Commit
```

Preflight (`OPTIONS`, any API path): `204` with the two headers above and

```
Access-Control-Allow-Methods: GET, PUT, POST, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type, If-Match, If-None-Match, WDS-Commit
Access-Control-Max-Age: 600
```

Never `Access-Control-Allow-Credentials`, never `Allow-Origin: null` or an echoed origin. Preflights are not
authenticated and not rate-limited.

Library files `/datastore/client/wds-<version>.js`: `Content-Type: text/javascript; charset=utf-8`,
`Access-Control-Allow-Origin: *`, `Cross-Origin-Resource-Policy: cross-origin`,
`Cache-Control: public, max-age=31536000, immutable`. The SRI hash (`sha384-<base64 with padding>`) is published
next to each file as `wds-<version>.js.sri`. A released file is immutable: `node build.mjs --freeze` marks a version as
frozen in `dist/hashes.json`, and the build then refuses to produce different bytes for it. Until a version is frozen (`frozen: false`, the
state of `wds-1.0.0.js` at the time of writing) it is rebuilt freely.

## 9. Operator API

Bearer `wdsop.…` (2.2). Same conventions, CORS and error format. Every call is written to the audit log, a failed vault call
as well (action `<name>_failed`, e.g. `recovery_start_failed`, with the error code as detail, written in a separate
transaction); a failed operator authentication is not audited (it counts toward the rate limit).

| Method and path | Purpose | Request | Response |
|---|---|---|---|
| `POST /admin/scopes` | create scope (tests, dev CLI) | `{"slug","name","join_code","limits"}`; `join_code` and `limits` may be `null` (defaults) | `201` operator scope object (below) |
| `PATCH /admin/scopes/{scope}` | suspend / resume / change settings | any subset of `{"status","join_code","limits","name"}` (`join_code: null` generates a new code; `enrollment` and `hibp` are refused with `400`); a `limits` value of `null` resets that limit to the default | `200` operator scope object (below); `409 limit_below_stored_value` |
| `GET /admin/vaults/{v}` | status | – | `200 {"vault","scope","created","deleted","epoch","roster_version","bytes","recovery"}`; `deleted` and `recovery` may be `null` |
| `POST /admin/vaults/{v}/recovery` | start recovery | `{"recovery_code":"<28 symbols>"}` | `201 {"requested","ready_at"}` |
| `DELETE /admin/vaults/{v}/recovery` | cancel | – | `200 {"cancelled":true}` |
| `GET /admin/vaults/{v}/escrow` | material for `wds-recover` | – | `200` below |
| `POST /admin/vaults/{v}/recovery/complete` | finish recovery | same body as `POST /vaults/{v}/roster` | `200 {"version","head","epoch"}` |

- **Operator scope object** (answer of `POST` and `PATCH /admin/scopes`): the document of `GET /scopes/{scope}` (8.3) with two
  differences: `limits` holds all six limits (`history_versions`, `max_envelope_bytes`, `max_value_bytes`, `vault_bytes`,
  `scope_bytes`, `max_vaults`), not the four public ones, and the object has `"join_code"` (string or `null`).
- **Lowering `max_value_bytes`:** `PATCH` refuses a `max_value_bytes` (also one that results from resetting it to a lower
  default) whose `max_envelope_bytes` is below the largest envelope stored in any version of any vault of the scope,
  deleted but not yet purged vaults included: `409 limit_below_stored_value` with `limit` = `"max_value_bytes"`,
  `largest_envelope_bytes` and `minimum_max_value_bytes` (the smallest value that would be accepted). Other changes in the
  same request are not applied then (7.1).
- **Start:** with a code, the server checks `SHA-256(code_bytes)` against `recovery_hash` (`403
  recovery_code_invalid`, counts as a failure) and sets `ready_at = now + 259200` (72 h). One pending recovery
  per vault (`409 recovery_pending`). Owners see it in `GET /slots/{access_id}` and can cancel it with `DELETE
  /vaults/{v}/recovery`.
- **Escrow fetch** requires a recovery with `now ≥ ready_at` (`409 recovery_not_ready`). Response:
  `{"vault","scope","epoch","roster":{"head","head_hash","versions":[…]},"escrow_slot":"<slot_id>","keyring_entry":"<b64u>"}`.
- **Complete** requires a ready recovery; the roster version MUST be signed by the escrow slot (`signer`) and is limited to
  adding exactly one slot, kind `invite`, role `owner`: same `epoch`, identical `commit` object, every existing slot
  (the escrow slot included) unchanged in every field, nothing removed (`400 invalid_roster` otherwise; this is exactly
  what the client verifier accepts for an escrow-signed version, so the server never stores a head that clients refuse,
  6.3). The rules for added slots (new slot ID and access ID, expiry within 15 days), `version`/`prev` and the no-op rule
  apply as in 6.3. An escrow-signed version is accepted only here, never through `POST /vaults/{v}/roster`. Marks the
  recovery completed. A tool that signs with a *retired* escrow set must set `time` ≤ `until` of that set, or clients
  refuse the version (6.5).

## 10. Non-API routes (informative)

Under `/datastore/` the same server serves the dashboard and login.psi integration (HTML; session cookie
`__Host-wds_session`, `Path=/; Secure; HttpOnly; SameSite=Strict`), `/datastore/client/…`, `/datastore/docs/…`,
`/datastore/llms.txt`, `/datastore/privacy`, `/datastore/export/` and `/datastore/healthz` (`200 {"status":"ok","read_only":bool}`).
These are specified elsewhere; the API under `/datastore/api/v1` never reads cookies.

`GET /datastore/client/hashes.json` returns the file `client/dist/hashes.json` of the deployed library build: `{"<version>": {"file", "sri", "sha256", "bytes", "escrow_pins", "retired_escrow", "frozen"}}`
(`Cache-Control: no-cache`, `Access-Control-Allow-Origin: *`, `Cross-Origin-Resource-Policy: cross-origin`). `wds-verify` reads the published integrity hashes from it.

**Library conventions that are visible in records (informative).** A *collection* (`store.collection(prefix)`) keeps one ordinary record next to its items, `<prefix without "/">.index`
(`notes/` → `notes.index`), whose JSON value is `{"wds":"collection/1","items":{"<id>":{"c":<creation ms, for sorting only>,"v":<version of the item record the entry describes>,"m":{…meta, at most 512 bytes…}}}}`.
The library merges changes by replaying its pending operations (add or replace an entry, remove an entry) on the last index it read, using `If-Match` on the index record; an operation that carries a record
version lower than the entry's `v` is dropped. No clocks or tombstones are involved. The server sees an ordinary record.

## 11. Flows (informative)

| Flow | Steps |
|---|---|
| Create | `GET /scopes` → generate founder E/S, vault ID, slot IDs, access ID, salt, VMK[1], NK, recovery code → Argon2id → wrap → roster v1 signed → keyring for founder + escrow → `POST …/vaults` → access sheet |
| Unlock | `GET …/kdf` → Argon2id → `GET /slots/{id}` (token) → unwrap, check vault → `GET …/roster` → verify chain → open keyring entry, check commitments → records |
| Invite | owner: new slot (E/S, invite secret, access ID), wrap under invite `K_wrap` → roster n+1 + full keyring + `new_slots` → show invite code |
| Redeem | parse code → `GET /slots/{id}` with invite token → unwrap → new E/S, renewal statement → Argon2id → `POST …/redeem` |
| Adopt renewal | owner unlock sees `slots[…].renewal` → verify signature → roster n+1 with new keys, kind passphrase → full keyring |
| Cancel invite | never used: roster n+1 without the slot, same epoch. Used (a request with its token was accepted) or redeemed: as Revoke |
| Expired invites | owner unlock: all unredeemed expired `write`/`read` invites removed in one version (as Cancel invite; as Revoke if one was used); the server never removes them (6.3) |
| Revoke | roster n+1 without slot, epoch+1, new VMK, commitments for all live epochs → full keyring → rekey loop → when own listing shows no old epoch: roster n+2 dropping old commitments |
| Recovery | operator: start → wait → escrow fetch → decrypt with escrow E → roster signed by escrow S adding an owner invite → complete → invite code to user |

**Member labels (informative).** The share dialog names members with notes that the library keeps in the vault as an
ordinary record named `.wds/labels` (the UI layer reserves names starting with `.wds/`: it refuses them from apps and hides
them from `list` and from exports). Anyone with write
access can change that record and the labels are not signed, so the dialog shows them as unverified: the slot ID is
shown next to every name and the revocation dialog repeats it.

## 12. Test vectors

The client implementer generates `client/test/vectors.json` with a script (`client/test/make-vectors.mjs`,
Node 26, WebCrypto plus the vendored Argon2id; `node:crypto` MAY be used only to compute public keys from fixed
private scalars) and commits both. The server's unittest and the tools reuse the file. The client test suite
re-derives every value and compares; for ECDSA it verifies (signatures are randomised, so the stored signature is one
valid sample).

Conventions: raw bytes as lowercase hex; wire strings (b64u, IDs, JSON documents) exactly as on the wire. Fixed
inputs: `seq(n, s)` = bytes `s, s+1, …` (mod 256) of length n. Private scalars: `d_<name> = SHA-256(ascii("wds1-vector-<name>"))`.
Every nonce is fixed (`seq(12, 0x40)`, `seq(12, 0x50)`, …).
